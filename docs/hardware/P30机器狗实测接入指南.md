## 1. 架构：两台计算单元，别搞混

```
Thor（开发机）
  192.168.20.25 (mgbe0_0)
  192.168.1.50  (辅助地址，需手动加)
        │ 网线直连 1 Gbps
        │
        ├── 192.168.1.100   ← 算力单元（Jetson Orin Nano）
        │     ├ SSH 22 (nano/123)
        │     ├ FTP 21 (vsFTPd 3.0.5)
        │     ├ HTTP 8080 (SlamNaviApp 地图/状态页)
        │     └ 7447 zenoh  ← 只跑 SLAM/导航，**无运动控制**
        │
        ├── 192.168.1.123   ← 运动控制单元
        │     ├ SSH 22 (凭据未知)
        │     ├ FTP 21
        │     ├ 80
        │     └ 7447 zenoh  ← **真正的 SDK 服务端（全部模块在这）**
        │
        ├── 192.168.1.11    ← 无开放端口（可能是雷达/相机）
        └── 192.168.1.122   ← 无开放端口
```

### 关键结论

**SDK 必须连 `192.168.1.123:7447`，不是 `.100`。**

连 `.100` 会出现所有查询超时（`command reply timeout`），因为那台只跑 SLAM/导航，没有运动控制、电源、关节的发布者。

实际发布顺序是 **FL → RL → FR → RR**（左前、左后、右前、右后）。
**必须按 `name` 对齐，不能假设下标。**

## 7. low_level 模块逐条核对（官方文档 vs 机器狗上的 .pyi/.h）

> 核对日期：2026-11-03
> 依据：机器狗本地安装的 `latentos_sdk/low_level.pyi`、`latentos_sdk/_native/low_level.pyi`、
> `/data/latentos/sdk_cpp/include/latentos/sdk/low_level/*.h`，加运行时实测。
> 对照文档：`latentos-developer-docs/docs/api/cpp/low-level.md`

### 7.1 结论先说

**C++ 接口和文档完全一致**，`joint_state.h` / `joint_command.h` / `low_level_client.h` 逐字段对得上。
**Python 绑定和文档不一致**，文档本身就是 C++ 文档，Python 侧有 4 处会导致代码写不出来。

### 7.2 Python 真实接口（`low_level.pyi` 原文）

```python
class LowLevelClient:
    def __init__(self, session: Session) -> None: ...
    def close(self) -> None: ...
    def __enter__(self) -> LowLevelClient: ...
    def __exit__(self, *exc: Any) -> None: ...
    @property
    def dropped_callbacks(self) -> dict[str, int]: ...
    def subscribe_joint_state(
        self, callback: Optional[Callable[[JointState], None]] = None) -> None: ...
    def get_latest_joint_state(self) -> JointState | None: ...
    def send_joint_command(self, command: JointCommand) -> None: ...
```

**没有 `unsubscribe_joint_state()`**（文档 C++ 有 `UnsubscribeJointState`）。

### 7.3 实测差异表

| 项目 | 文档（C++） | Python 实测 | 影响 |
|---|---|---|---|
| 订阅 | `SubscribeJointState(cb)` | `subscribe_joint_state(callback=None)` | 参数可选，不传回调就只写缓存 |
| 退订 | `UnsubscribeJointState()` | **不存在** | 只能 `close()` 整个 client |
| `events` 分支 | 无 | native 层 `subscribe_joint_state(events: bool=False)`；`events=True` 返回 `_JointStateQueue`（含 `drain()` / `dropped`） | Python 包装层未暴露，只能拿最新帧 |
| `dropped_callbacks` | 无 | 存在，字典 `{'subscribe_joint_state': N}` | 可监控丢帧 |
| 上下文管理 | 无 | 支持 `with LowLevelClient(sess) as ll:` | — |
| `JointCommand` 构造 | 聚合初始化 | `JointCommand(**kwargs)`，字段可读写 | **必须用 kwargs 或逐字段赋值** |
| `heart` 类型 | `int16` | Python 侧 `Sequence[int]`，>32767 抛 `TypeError` | 上界 32767 = `0x7fff`，与文档一致 |
| 长度一致性 | "应一致" | **设置时不校验**，只在发送时按 `position.size()` 取 | 长度不齐会静默出错，自己保证 |
| 默认值 | — | 所有数组默认空 `[]`，`heart` 也是 `[]` | 不做 `heart=[]` 以外的初始化 |

### 7.4 `_JointStateQueue`（文档完全没写）

native 层才有，`events=True` 时返回：

```python
q = native_ll.subscribe_joint_state(True)
q.dropped   # int，累计丢弃帧数
q.drain()   # list[JointState]，一次性取走缓冲区
```

实测：缓冲区**固定 256 帧**，满了就丢并且只计数。空转 10 秒 `dropped` 涨 4749，即约 **475 Hz**；持续 drain 5 秒拿到 2497 帧，即 **499 Hz**。

> 注意：`events=True` 时 `get_latest_joint_state()` 仍然有数据（双路并存）。

### 7.5 关节状态实测（`sit_down` 姿态）

```
send_time_ns = 1793694129655709673   joint_num = 16
state_num 全 4096   err_num 全 0   heart 全 0   pcb_temp 全 0
motor_temp = [29,28,27,30, 30,29,28,31, 29,28,29,32, 30,28,28,31]
```

- `state_num = 4096` 是电机使能位（`0x1000`），**全是 4096 说明 16 个电机都在使能状态**
- `err_num` 全 0，无故障
- `pcb_temp` **全 0**，实际没填，不要用来做温度保护
- `heart` 全 0，发布端没用心跳字段

### 7.6 文档说"用 12 个关节"，本机是 16 个

文档发送示例列了 12 个关节名（`FL/FR/RL/RR` × `hip/thigh/calf`）。
本机实际发布 **16 个**，每条腿多一个 `*_foot_joint`（轮）：

```
FL_hip_joint  FL_thigh_joint  FL_calf_joint  FL_foot_joint
RL_hip_joint  RL_thigh_joint  RL_calf_joint  RL_foot_joint
FR_hip_joint  FR_thigh_joint  FR_calf_joint  FR_foot_joint
RR_hip_joint  RR_thigh_joint  RR_calf_joint  RR_foot_joint
```

发送命令时如果只写 12 个，`position.size()=12`，SDK 就按 12 个下发；剩下 4 个轮子没有任何控制源，行为未定义。**轮式机型必须发 16 个。**

### 7.7 发布顺序 FL → RL → FR → RR

文档示例按 FL/FR/RL/RR 排列，本机实际是 **FL → RL → FR → RR**。
**必须按 `name` 对齐**，不要用下标。

### 7.8 实际姿态与零点

当前 `current_group='sit_down'`，IMU 由四元数算出的横滚/俯仰/偏航 ≈ `(0.3, -1.0, -0.7)°`（基本水平）。
此时 thigh ≈ `+3.1 rad`、calf ≈ `-2.5 rad`——这是**趴卧位**，不是站立零位。
直接用文档示例的 `position=0` 会让腿猛然伸向零位，**上真机前必须改成按当前角度对齐**。

### 7.9 安全要点（文档说过，这里补充实测依据）

- `SendJointCommand` 直接写 `latentos/joint_command_mit`，**无仲裁、无 ACK**
- 必须先 `switch_group("joint_test", "")`，否则和 motion_control 抢同一话题
- 本机 `send_velocity` / `switch_group` 已有真实实现，但**尚未在真机上验证动作**（本次只做只读）
- 文档 100 Hz 发送、`stiffness=100 / damping=2 / max_effort=50` 是仿真参数，真机需重标定

## 8. 导航与点云（实测打通）

> 实测日期：2026-11-03
> 关键结论：**点云不走 SDK `nav` 模块，走 SlamNaviApp 的 zenoh**。

### 8.1 两个完全独立的系统，别混

`.100` 上跑着**两套互不相干的软件**：

| | LatentOS SDK（运动控制） | SlamNaviApp（导航/建图） |
|---|---|---|
| 进程 | 无（只有库） | `/opt/data/bin/bin/SlamNaviAppCppNode` PID 1991 |
| 端口 | `7447` | `7447` **也是它** + `8080` HTTP |
| 数据 | motion/power/low_level | 点云、位姿、路径、导航任务 |
| 谁在跑 | `.123` 是服务端，`.100` 是客户端 | `.100` 自己就是服务端 |

> ⚠️ **之前测 motion/power 时 `.100:7447` 超时，不是因为没服务，而是因为那个 7447 是 SlamNaviApp 的 zenoh，不提供运动控制模块。** 两个系统共用端口号，容易误判。

`SlamNaviAppCppNode` 的参数（`ps aux` 可直接看到）：
```
--livo   .../mapping/mid360_online_livo.yaml     # LIO 建图
--reloc  .../mapping/mid360_reloc_params.yaml    # 重定位
--global .../planner/global/params_createMap.yaml
--local  .../planner/local/params.yaml
--controller .../planner/controller/params.yaml
--sdk    .../mapping/MID360s_config.json         # 雷达网络
--sdk_client.yaml -> tcp/192.168.1.123:7447      # 它反过来连运动控制
--port=8080
```

### 8.2 雷达：Livox MID360

`/opt/data/bin/config/robot/BigDog_Wheel/mapping/MID360s_config.json`

| 项 | 值 |
|---|---|
| 雷达 IP | **192.168.1.122** |
| 型号 | Livox MID360（`lidar_type: 8`，`lidar_summary_info`） |
| 点云端口 | 雷达 56300 → 主机 **56301** |
| IMU 端口 | 56400 → **56401** |
| 命令/推送/日志 | 56101 / 56201 / 56501 |
| 主机 IP | 192.168.1.100 |

**实测流量**：`2.86 MB/s`、`2306 pkt/s`（4 秒采样），雷达 ping 1.2 ms 在线。
日志每帧约 `pts=20160`（原）→ 去畸变后 `7786` 点。

### 8.3 三条拿点云的路（从易到难）

#### 路 A：直接抓雷达原始 UDP（最简单）

雷达裸 UDP 就在 `192.168.1.100:56301`，是 **Livox 私有协议**，不是 ROS。
需要 Livox-SDK2 或 `livox_ros_driver2` 解析。适合要**实时全速率**（10 Hz × 2 万点）。

#### 路 B：SlamNaviApp 地图点云（已完全打通 ✅）

**这是目前最实用的路径**：地图 PCD 通过 zenoh 按块推送。

**完整协议（逆向实测确认）：**

```
topic:  maps/<mapId>/maps/pcd/chunk        # 全局/稠密地图
topic:  maps/<mapId>/maps/pcd/trav/chunk   # 可通行区域地图
```

payload 二进制布局（小端）：

| 偏移 | 类型 | 内容 |
|---|---|---|
| 0 | u32 | mapId 长度 |
| 4 | bytes | mapId（ASCII） |
| +0 | u32 | 文件名长度 |
| +4 | bytes | 文件名，如 `cloudGlobalDense.pcd` |
| +0 | u32 | chunk index（从 0） |
| +4 | u32 | chunk total（总块数） |
| +8 | u32 | chunk_size（通常 49152 = 48 KiB） |
| +12 | bytes | PCD 数据片段 |

**实测验证**：`map_5255568` 的 `cloudGlobalDense.pcd`
- 37 块，每块 49152 字节，协议头 **51 字节**
- 重组后 **1,777,518 字节**，与磁盘文件**字节级完全一致**
- PCD 头：`FIELDS x y z intensity`，`POINTS 111083`，`DATA binary`
- 校验：`hdr_end + POINTS × 16 == 总字节` → **OK**

触发下发：
```http
POST http://192.168.1.100:8080/api/v1/maps/pcd/publish
{"mapId": "map_5255568"}
→ {"code":0}
```

> 注意：**这是"请求即推送"**，服务端只在收到 POST 后推一次，不会持续广播。

#### 路 C：SDK `nav` 模块（几乎没用）

```python
nav = NavClient(sess)
nav.advertise_point_cloud_stream("192.168.1.100", 19001, True)
```
- 它**只发布一条"我这有个端口可以收点云"的通告**，到 topic `latentos/nav/pointcloud/stream/info`
- **不编码、不传输任何点云**
- 实测：按 1 Hz 通告 10 次，**SlamNaviApp 完全没有连过来**（`SlamNaviAppCppNode` 二进制里根本没有 `nav/pointcloud` 这个字符串，也没链接 `liblatentos_sdk_nav.so`）
- 结论：**这条路在当前固件上是死路**。官方文档说的 "advertise endpoint" 需要一个订阅该通告的桥接程序，而机器狗上没装。

### 8.4 zenoh 完整 key 表（从二进制提取）

前缀规则：**`maps/<mapId>/` + 下面的 key**

| key | 方向 | 说明 |
|---|---|---|
| `sys/status` | 发布 1 Hz | 主机 CPU/内存/磁盘/温度 + 定位状态 |
| `live/pose` | 发布 | 实时位姿 |
| `live/pointcloud` | 发布 | **实时点云**（IDLE 时不发） |
| `live/navstate` | 发布 | 导航状态机 |
| `live/vel` | 发布 | 速度指令 |
| `live/path` | 发布 | 规划路径 |
| `live/keyframes` | 发布 | 关键帧 |
| `live/traversable` | 发布 | 可通行栅格 |
| `live/inflated` | 发布 | 膨胀层 |
| `maps/pcd/chunk` | 发布 | 地图点云分块 |
| `maps/pcd/trav/chunk` | 发布 | 可通行地图分块 |
| `system/status` | — | 实际不活跃 |
| `/tasks/*/result` | 发布 | 任务结果（reloc/globalplan/gohome…） |
| `/tasks/navpoint/progress` | 发布 | 导航进度 |
| `/session/waypoint/result` | 发布 | 航点结果 |

**实测：IDLE 状态下只有 `sys/status` 在发（1 Hz，375 字节 JSON）。**
其余 `live/*` 全部静默——因为没在建图/导航。

### 8.10 Python 侧拿点云的完整可用代码

```python
import json, struct, urllib.request
import zenoh

EP = "tcp/192.168.1.100:7447"
MAP_ID = "map_5255568"

conf = zenoh.Config()
conf.insert_json5("connect/endpoints", json.dumps([EP]))
conf.insert_json5("scouting/multicast/enabled", "false")
sess = zenoh.open(conf)

chunks = {}
def cb(sample):
    p = sample.payload.to_bytes()
    o = 0
    n = struct.unpack_from("<I", p, o)[0]; o += 4
    map_id = p[o:o+n].decode(); o += n
    n = struct.unpack_from("<I", p, o)[0]; o += 4
    fname = p[o:o+n].decode(); o += n
    idx, total, csize = struct.unpack_from("<III", p, o); o += 12
    chunks[idx] = (total, fname, p[o:])

sub = sess.declare_subscriber("maps/%s/maps/pcd/chunk" % MAP_ID, cb)

req = urllib.request.Request(
    "http://192.168.1.100:8080/api/v1/maps/pcd/publish",
    data=json.dumps({"mapId": MAP_ID}).encode(),
    headers={"Content-Type": "application/json"}, method="POST")
urllib.request.urlopen(req, timeout=15).read()

# 等收集齐
import time
for _ in range(100):
    if len(chunks) and len(chunks) == next(iter(chunks.values()))[0]:
        break
    time.sleep(0.1)

total = next(iter(chunks.values()))[0]
pcd_bytes = b"".join(chunks[i][2] for i in range(total))
open("map.pcd", "wb").write(pcd_bytes)
print("PCD", len(pcd_bytes), "bytes,", chunks[0][1])
```
