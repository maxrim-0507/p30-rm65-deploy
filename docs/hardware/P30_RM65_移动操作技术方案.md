## 2. 可用动作空间（实测结论）

> 核心认知：**端到端不等于输出关节力矩**。主流 VLA（π0、GR00T N1.x、OpenVLA）
> 的标准输出本来就是「末端位姿增量 + 夹爪 + 底盘速度」，恰好是当前能拿到的空间。

| 层级 | 接口 | 频率 | 状态 |
|---|---|---|---|
| 底盘 · 连续速度 | `send_velocity(vx, vy, ωz)` | 目标 50 Hz | ❌ F1 超时 |
| 底盘 · 导航目标点 | `POST /api/v1/session/waypoint/setgoal` | 事件触发 | ⚠️ 待 F2 修复 |
| 底盘 · 全局路径 | `/api/v1/tasks/plan/globalpath/request` | 事件触发 | ⚠️ 待 F2 修复 |
| 底盘 · 位姿反馈 | zenoh `live/pose` | ~10 Hz | ⚠️ 需导航运行 |
| 底盘 · IMU | `TelemetryClient` | 500 Hz | ✅ 可用 |
| 机械臂 · 关节 | RM65 SDK（以太网） | 100–200 Hz | ✅ 独立可控 |
| 机械臂 · 笛卡尔 | RM65 SDK movej/movel | 100 Hz | ✅ |
| 机械臂 · IO | RM65 SDK | 事件 | ✅ |
| 夹爪 | RM65 末端 IO / RMG24 | 事件 | ✅ |
| **腿关节** | `send_joint_command` → `latentos/joint_command_mit` | 500 Hz | 🚫 **按约束禁用** |

### 2.1 由此推出的三条设计原则

**原则一：动作空间 = (底盘动作, 臂 6D 位姿增量, 夹爪开合)**
不做关节空间端到端。臂的 IK 在 L2 求解，解出的 6 个关节目标走 RM65 自己的 SDK。

**原则二：移动与操作交替执行，不做边走边抓**
不能全身控制 → 底盘运动中无法补偿臂的反作用力矩。
因此采用 `navigate_to → 停稳 → manipulate → navigate_to …` 的串行范式。
这与公开方案 [2512.01052](https://arxiv.org/abs/2512.01052)（导航到点后抓取，75%）一致。

**原则三：工作空间不足时用底盘微移补偿**
失去 WBC 的「身体倾斜扩展可达范围」能力后，用 `底盘前进/横移 10–20 cm + 重新 IK` 替代。
规则式实现，不需要学习，能补回 WBC 的大部分收益。

## 3. 总体架构

```
┌──────────────────────────────────────────────────────────────────┐
│ L3 任务层 / 大脑 —— Thor（1–3 Hz）                                │
│                                                                  │
│   语言指令 ──→ 任务分解 ──→ 目标 grounding ──→ 技能序列           │
│   全景 RGB-D ─→ 场景图（物体 6D 位姿）──→ 可达性判断              │
│   模型：Qwen2.5-VL-7B 级 VLM（不微调，prompt + 场景图）            │
│   输出：navigate_to(x,y,yaw) / pick(target_id) / place(pose)      │
├──────────────────────────────────────────────────────────────────┤
│ L2 技能层 —— Thor（10–30 Hz）                                     │
│                                                                  │
│   ┌────────────┐  ┌─────────────┐  ┌──────────────────────────┐  │
│   │ Nav 技能    │  │ Pregrasp    │  │ Manipulate 技能           │  │
│   │ 导航目标下发 │  │ 标定 + IK   │  │ VLA 策略 / 或经典闭环     │  │
│   │ + 到位判定   │  │ + 底盘微移   │  │ 输出 EEF 6D 增量 + 夹爪   │  │
│   └────────────┘  └─────────────┘  └──────────────────────────┘  │
│                                                                  │
│   技能管理器：状态机 / 超时 / 重试 / 成功判定                      │
│   IK 求解：EEF 6D → RM65 6 关节角                                  │
├──────────────────────────────────────────────────────────────────┤
│ L1 执行层（厂商负责，不可改）                                      │
│                                                                  │
│   狗：平衡控制 / 步态 / 速度平滑 / 安全限幅 / 急停                 │
│   臂：RM65 驱动器 / 关节伺服 / 碰撞检测                           │
└──────────────────────────────────────────────────────────────────┘
                 ▲                              ▲
                 │ 以太网（有线，禁用 WiFi）      │
        ┌────────┴────────┐            ┌────────┴─────────┐
        │ P30W 机载        │            │ RM65 控制箱       │
        │ Orin Nano 8GB    │            │ 独立以太网        │
        │ → 后期 Orin NX   │            │                  │
        └─────────────────┘            └──────────────────┘
```

### 3.1 为什么必须三层，而不是一个大网络直通

| 维度 | 分层 | 单网络端到端 |
|---|---|---|
| 安全 | L1 由厂商兜底，VLA 输出异常最多触发急停 | 网络崩溃即失控 |
| 算力 | L3 可低频、L2 可换模型 | 需要同时满足 1Hz 和 30Hz，浪费算力 |
| 数据 | L2 可独立训练/替换 | 任一环变化需整体重训 |
| 调试 | 每层可单独回放 | 黑盒 |

### 3.2 与厂商固件的关系

不改动、不绕过厂商控制器的任何安全逻辑。我们只做**指令的生成方**，所有动作仍经过厂商的仲裁与限幅。

## 4. 端到端方案：网络输入输出定义

### 4.1 VLA（L2）输入

| 模态 | 规格 | 来源 | 备注 |
|---|---|---|---|
| 头部 RGB | 640×480，10–15 Hz | `front_0` RTSP 或外接 USB 相机 | 机载相机 90 fps 能力过剩，取 15 Hz 即可 |
| 腕部 RGB | 640×480，15 Hz | 外接（推荐） | SLIM 证明单腕部 RGB 可达 ~80% |
| 深度 | 对齐到头部 RGB | RealSense / OAK-D / 雷达投影 | 可选，用于 3D grounding |
| 本体状态 | 底盘速度 + 位姿 + 臂 6 关节角 + 夹爪开度 | IMU + `live/pose` + RM65 | ~20 维 |
| 语言 | 任务指令字符串 | L3 下发 | 可预先编码缓存 |

**相机方案建议**：机载 `front_0` 的 MJPEG 640×480@90 编码质量与延迟未知，且只提供 2D。
**建议外接一台 RGB-D**（如 RealSense D435i / OAK-D Pro），同时解决：深度、时间戳同步、低延迟。
这台相机挂在 Thor 上，与 P30 自带相机系统解耦。

### 4.2 VLA（L2）输出

| 输出 | 维度 | 语义 | 执行方式 |
|---|---|---|---|
| EEF 位置增量 | 3 | 世界系或臂基座系 Δxyz（m） | IK → RM65 |
| EEF 姿态增量 | 3 | Δrpy 或 6D 旋转表示 | 同上 |
| 夹爪 | 1 | 0–1 归一化开度 | RM65 IO |
| 底盘动作 | 3 | (vx, vy, ωz) 或离散 `{前进, 后退, 左移, 右移, 停}` | 修 F1 前用离散 |
| 终止标志 | 1 | 技能完成 / 失败 | 技能管理器 |

**为什么用增量而不是绝对位姿**：增量对相机外参标定误差更鲁棒，且易于做动作分块（action chunking）。
这也是 π0 / GR00T 的通行做法。

### 4.3 两类 L2 实现（可切换）

| | 4.3.A 经典闭环（先做） | 4.3.B VLA 策略（后做） |
|---|---|---|
| 感知 | 检测 + 6D 位姿估计 | 端到端 RGB → 动作 |
| 抓取 | GraspNet / 几何规则 | 模仿学习策略 |
| 泛化 | 只对已知物体类 | 对训练分布内物体 |
| 数据需求 | 无（零样本） | 数百条示范 |
| 成功率参考 | 75%（[2512.01052](https://arxiv.org/abs/2512.01052)） | ~80%（[SLIM](https://arxiv.org/abs/2501.09905)） |
| 调试成本 | 低，每步可解释 | 高，需数据诊断 |

**建议先做 A 再切 B**：A 用于打通全链路、验证标定、积累数据；B 作为最终形态。

## 5. 算力分配与演进路径

### 5.1 三级算力对比

| | Orin Nano Super 8GB（现在） | Orin NX 16GB（计划） | Thor（现有） |
|---|---|---|---|
| 实测内存 | 7.4 GiB 可用 | ~15.5 GiB（标称） | **122 GiB**（`free -g` 实测） |
| CPU | 6× A78AE @1.728 GHz | 8 核 | 14 核 |
| AI 算力（厂商标称） | 67 TOPS INT8 | 100 TOPS INT8 | 更高（未核实具体值） |
| 能跑 VLM 7B | ❌ | ❌ | ✅ |
| 能跑 VLA 3B | ❌ | ⚠️ 勉强（INT8/FP8，需实测） | ✅ |
| 能跑点云处理 | ❌ | ⚠️ | ✅ |
| 位置 | 狗身 | 狗身 | 外挂 |

> Orin Nano / NX 同为 SO-DIMM 接口，理论可换，但 **NX 功耗上限更高（25W），散热模组是否匹配必须问厂商**。
> 见 §10 第 2 项。

### 5.2 算力分工（当前阶段）

| 模块 | 运行位置 | 理由 |
|---|---|---|
| SlamNaviApp（SLAM/导航） | Orin Nano | 厂商预装，无法迁移 |
| 相机推流 / RTSP 解码 | Orin Nano | 就近 |
| 检测（YOLO 级） | Orin Nano（可选） | 轻量，省带宽 |
| **VLM 7B（L3）** | **Thor** | Nano 装不下 |
| **VLA 3B（L2）** | **Thor** | Nano 装不下 |
| **IK 求解** | **Thor** | 与 VLA 同机，省一跳 |
| **点云处理 / 场景图** | **Thor** | 地图 PCD 已打通，可直取 |
| 数据录制 / 时钟同步 | Thor | 统一时间基准 |

**Nano 上的内存实测**：`memTotalMb = 7620`，当前 `memUsedMb ≈ 1274`，跑着 SlamNaviApp。
剩余约 6.3 GiB。**再加一个 VLA 推理进程会直接 OOM**。

### 5.3 Thor 外挂的工程问题

| 问题 | 现状 | 对策 |
|---|---|---|
| 重量 | Thor 开发套件约 2 kg 量级（未实测） | 40 kg 额定负载下无压力 |
| 供电 | P30W 单电池 936 Wh | 需 46.8V → Thor 输入电压降压模块 + 浪涌保护 |
| 散热 | 开发套件自带风扇 | 需防护外壳，注意 IP67 会被破坏 |
| 震动 | 轮足底盘震动小于四足，但仍存在 | 减震安装座；Thor 内部有 NVMe，需确认抗震等级 |
| 网络 | WiFi 延迟 20–100 ms 抖动 | **必须有线以太网直连**，禁用 WiFi 做控制回路 |
| 长时形态 | 外挂不适合交付 | 后期考虑定制工控盒方案（Orin NX/AGX Orin 级） |

### 5.4 关于「最终形态」

三种演进路线，成本递增：

| 方案 | 描述 | 风险 |
|---|---|---|
| S1 | 长期外挂 Thor | 适合研发期，不适合交付 |
| S2 | 换 Orin NX 16GB，Thor 只做训练 | VLA 3B 能否在 NX 上实时跑需实测 |
| S3 | 定制 AGX Orin 级工控盒上机 | 成本高，周期长 |

**建议**：研发期用 S1，产品化前评估 S2。不建议现在决定 S3。

## 6. 数据采集与训练

### 6.1 前提：先修 F3（RTC）

数据采集的所有前提中，**时间同步的优先级高于一切**：

- 相机帧、臂关节、底盘位姿三路时间戳必须可对齐
- 当前系统时间 1970，日志文件名即证据
- 修法：换 RTC 电池 / NTP 对时 / 由 Thor 做统一时钟源

**建议方案**：Thor 作为 NTP/PTP 主时钟，狗与 RM65 控制箱都从它同步。
若厂商固件不允许改时间，则采用**硬件触发**（相机 trigger out 打标 + 各端记录接收时刻）作为兜底。

### 6.2 示范采集的输入源

| 模态 | 采集方式 |
|---|---|
| 臂遥操作 | Realman 官方遥操作套件（主从臂）或手柄控笛卡尔 |
| 底盘遥操作 | 手柄 → 导航目标点（F1 修好后可连续速度） |
| 相机 | 头部 + 腕部 RGB（与推理时一致） |
| 本体状态 | RM65 关节 100 Hz + IMU 500 Hz + `live/pose` |

### 6.3 数据规模（参考公开方案）

| 论文 | 数据量 | 实现方式 |
|---|---|---|
| [SLIM](https://arxiv.org/abs/2501.09905) | 纯仿真训练，零真实数据 | RL + teacher-student |
| [2605.15713](https://arxiv.org/abs/2605.15713) | 未明确，6 个场景验证 | 分层 RL |
| 常规 IL 经验值 | 单任务 50–200 条示范 | 行为克隆 / ACT |

**判断**：既然不能做 RL（无关节控制），就只剩模仿学习。单任务先按 **100 条** 起步，
用 ACT / Diffusion Policy 这类轻量方法验证可行性，再决定是否升级到 GR00T 级 VLA。

### 6.4 训练在哪

| 环节 | 位置 |
|---|---|
| 数据存储 | Thor（122 GiB 内存，NVMe） |
| 轻量训练（ACT / DP） | Thor 本地可跑（需实测） |
| VLA 微调（GR00T / π0） | **云端 H100/L40**（既有 `docs/开发方案_GR00T_N1.7云端训练与Thor部署.md` 可复用） |
| 推理部署 | Thor（TensorRT 导出） |

## 7. 与公开方案的对照

### 7.1 三条技术路线

**路线 A — 分层 ROS 管线**
[2512.01052](https://arxiv.org/abs/2512.01052) ROS 分层：导航 → 检测 → GraspNet，75%（12 次）。
[2603.07866](https://arxiv.org/abs/2603.07866) 开放词表检测 + 深度补偿 + 点云补全 + 6-DoF 抓取，9/10 vs 基线 3/10。
→ **与 P30 现有 SlamNaviApp 契合度最高**，是本案主线。

**路线 B — 学习型全身控制**
[SLIM](https://arxiv.org/abs/2501.09905) Go1 + WidowX-250S + 单腕部 RGB，纯仿真训练，≈80%。
[2512.18938](https://arxiv.org/abs/2512.18938) B1 + Z1，IsaacGym → MuJoCo → 真机，开源。
[2605.15713](https://arxiv.org/abs/2605.15713) 仿真 86.05%；真机 73.3%（≤1.3 kg，0–1.1 m，平均 4.06 s）。
[2412.03012](https://arxiv.org/abs/2412.03012) 轮足+臂，位置误差 <5 cm、姿态 <0.1 rad。
→ **全部依赖关节级控制**，本案无法直接采用，但可作为 L2 策略的训练思路参考。

**路线 C — 经典解耦控制**
[2307.04918](https://arxiv.org/abs/2307.04918) SAG + IBVS，HyQReal + 7-DoF。
[2508.14994](https://arxiv.org/abs/2508.14994) 视觉共享控制遥操作。
→ 作为 4.3.A 和调试基线。

### 7.2 硬件先例

| 平台 | 本体负载 | 机械臂 | 臂负载 / 自重 |
|---|---|---|---|
| **P30W（本案）** | 额定 40 kg / 极限 150 kg | RM65 | 5 kg / 7.2 kg |
| [Unitree B2 / B2-W](https://www.unitree.com/en/b2-w) | 站立 120 kg / 行走 >40 kg | Z1 | 2–3 kg / 4.3–4.5 kg |
| [Spot + Arm](https://bostondynamics.com/products/spot/arm/) | Spot 本体 | 6-DoF ≈1 m | 提 11 kg / 拖 25 kg（**靠全身配合**） |

**值得注意**：Spot Arm 官方明说「lift 11 kg but drag 25 kg，uses its whole body」——
厂商自己也承认单臂静态能力有限、必须全身配合。这从侧面说明本案放弃全身控制后，
**必须用「底盘微移 + 交替执行」来补偿**（§2.1 原则二、三）。

## 10. 待厂商确认清单

按优先级排序，前 3 项直接影响方案可行性：

**1. P30W 上装负载的力矩参数**
不只问「能装多重」，要问「**负载重心离安装面多远时仍满足额定负载**」。
RM65 前伸 610 mm + 5 kg 负载，静态力矩约 `(7.2×0.3 + 5×0.61)×9.8 ≈ 51 N·m`（粗略估算，重心位置待确认）。
需要拿到安装板的结构强度和推荐安装位置。

**2. Orin NX 升级套件**
是否提供？散热模组是否匹配 NX 的 25W？换装后保修如何？

**3. `send_velocity` 超时的原因**
是配置问题（`switch_group("locomotion")` 未执行）、固件问题，还是服务端已退出？
这条决定 VLA 的底盘动作是离散还是连续。

**4. `joint_test` 组是硬锁还是软约束**
实测 `send_joint_command` 能写入 `latentos/joint_command_mit`，但需要先 `switch_group("joint_test")`。
- 若是**软约束**（能开但不推荐）→ 未来可补 WBC 层，直接获得公开文献的性能上限（<5 cm 跟踪、边走边抓）
- 若是**硬锁**（固件禁用）→ 只能走本案的解耦路线

> **这是本次方案中价值最高的一个问题**。值得花一次沟通成本问清楚。

**5. RTC 是否可换电池/改时间**
固件是否允许系统对时？不允许则需硬件触发方案。

**6. 相机 `front_0` / `back_0` 的 Stream Profile 细节**
延迟、编码格式、是否有深度对齐能力、是否支持硬件时间戳。

**7. 是否有官方 URDF / MJCF**
用于仿真与 IK 标定。当前仓库无 URDF，需索取。

## 附：本方案的核心判断（一页纸）

1. **不能控关节 ≠ 不能做端到端**。VLA 的标准动作空间就是末端位姿 + 夹爪 + 底盘速度，现行接口够用。
2. **必须分三层**。Thor 跑 VLM+VLA，Orin Nano 只跑厂商导航与推流，安全由厂商 L1 兜底。
3. **移动与操作串行执行**。失去全身控制后，用「停稳再抓 + 底盘微移补位」替代。
4. **先经典闭环，再 VLA**。经典闭环打通链路、积累数据，VLA 是最终形态。
5. **P0 修复四项故障（时间同步 / 重定位 / 速度链路 / .123 凭据）之前，方案无法验证。**
6. **最值得问厂商的问题是 `joint_test` 是硬锁还是软约束**。若是软约束，整个技术路线可以升级。
